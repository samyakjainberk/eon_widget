EoS Prediction Widgets — a field guide

Everything the two prediction widgets compute and draw, in one place: the mental model, how a number travels from server.py to a plot, and a card for every section — what it shows, the math, where the data comes from, and how to change it.

mirrors index_prediction.html & index_prediction_multiclass.html backend server.py companion code reference_predictions.py
How to read this Skim §0 and §1 once for the mental model, then use it as a lookup: the naming map tells you which knob maps to which code symbol, and each section card is self-contained. Line numbers drift as the file changes — treat them as a starting point and confirm with the named function / DOM id, which are stable. The runnable reference_predictions.py re-implements the math in plain autograd so you can read the logic linearly.

0 · The big picture

Both widgets study one thing: what happens to the curvature of a network as full-batch gradient descent trains it — the Edge of Stability (sharpness climbs until it sits at 2/η and hovers) and progressive sharpening (the top Hessian/NTK eigenvalues grow during training). Every "★ Prediction" asks a version of the same question: can a simple linearized or frozen model of the network forecast that curvature growth? The other panels dissect the objects those forecasts are built from.

Everything on screen is assembled from a small cast of objects. Get comfortable with these and the whole widget reads easily:

θthe flat parameter vector, p = number of parameters.
f(θ)network outputs, shape (N, out); flattened to length M = N·out.
Jthe Jacobian ∂f/∂θ, shape (M, p). Row k is ∇θfk.
rthe residual, length M. MSE: r = y − f. CE (multiclass): r = onehot − softmax(f).
gthe loss gradient ∇θL. GD steps θ ← θ − η·g. (Note: J·r ≡ Jᵀr is the GN gradient, ∝ g for MSE.)
NTKJ Jᵀ, shape (M, M) — the tangent kernel in output space. Its top eigenvalue is the "NTK edge".
GNJᵀ J, shape (p, p) — Gauss-Newton. For CE this becomes the Fisher J̃ᵀΛJ̃.
Qk∇²θfk, the (p×p) Hessian of one scalar output — "per-sample function Hessian".
MrΣk rk Qk — the residual-weighted function Hessian. Also called Q_r. Drives most spectral panels.
HΣk Qk — the unweighted function Hessian (cotangent ≡ 1).
∇²Lthe full loss Hessian. λmax(∇²L) is the sharpness; EoS is sharpness ≈ 2/η.

The one identity worth memorizing — it's how nearly every spectral panel is computed:

Σk ck Qk = ∇²θ( Σk ck fk ) = the Hessian of the scalar (f·c)

So a residual-weighted (c = r) or unweighted (c = 1) function-Hessian is just the Hessian of one scalar — you get it from one Hessian-vector product (matrix-free, via hvpS) or, for a small MLP, materialize it whole (that's the new Q-eigenspectrum panel).

1 · Architecture & data flow

There is one backend, server.py, and two browser front-ends that are 98% identical — index_prediction.html (MSE / regression) and index_prediction_multiclass.html (CE / softmax). They differ by ~83 lines: presets and loss defaults, not new compute. A run flows like this:

01 · browser
Build params
Each enN checkbox → an opt map → sK flags. POST to /run.
02 · server
Train + measure
run_stream does GD; every step builds one record dict with many g_* keys.
03 · SSE
Stream records
Records stream back over Server-Sent Events, one per step (or eig-tick).
04 · browser
Draw
pushPoint(t, D) reads D.g_* and extends Plotly traces.
Toggles
A checkbox enX in the browser maps to a server flag sK. Some flags gate compute (off = not calculated); others only gate visibility (the data is always computed, the box just shows/hides the panel). The predictions 3, 4, 5.1, 5.2 are always computed (their enP* boxes only hide the DOM); the ray, adaptive-optimizer, and all the new/inherited diagnostics gate compute too.
Captures
A run can be saved to a .json (+ compact .min.json) and re-loaded later — the browser replays the records through the same pushPoint. Panels with a scrubber (Q-spectrum, §11, §12, §20, §22/23, §6, Prediction-6 scree) keep a per-snapshot history so you can slide back to any iteration.
Parity
The base widget also has a browser-only compute backend, so a few sections (§13, §14, §19, §20, §6) are recomputed client-side and must match the server byte-for-byte — when you change one of these, change both the Python and the JS. The predictions, self-stab, and Q-spectrum have no browser mirror (server-only). Note: this is about the recompute mechanism, not availability — on the prediction widget's GPU backend most inherited sections are gated off entirely (see the Inherited diagnostics caveat).

The ★ Predictions

Each prediction freezes some linearization of the network and asks whether it forecasts the real curvature dynamics. They share a shape: an anchor (a training event that triggers the freeze), a propagated theory, and an overlay of predicted vs actual. Solid = frozen-model theory, dashed = a richer (cubic/evolving) theory, dots = the actual run.

1&2The lr / σ sweep mode=sweeprun_sweepMSE only
What

SSSelf-stabilization mechanism enSS → ssg_ss
What

Inherited diagnostics

These come from the base widget and are documented here because they're wired into the prediction widgets' HTML and share the same J / r / M_r / NTK cast. But read the caveat first — most of them do not actually run on the prediction widget as shipped.

Gated off by default The prediction widgets force compute='gpu' and then, in currentQueryParams() (~index_prediction.html:5174), apply an ALLOW-list: {s1,s2,s3,s4,s5,s12,s14,s16,s17,s29,s35} — every other section flag is forced to '0'. So of the inherited group, only §6 (s29) and §7 (s35) compute server-side; §11, §12a, §12b, §18, §19, §20, §22, §23, §24, §25, §26, §13, §14 are OFF even if you tick their checkbox. The parity sections (§13/§14/§19/§20/§6) can still appear via the in-browser recompute, but only on the non-GPU backend (MLP/synthetic) — which the prediction widget doesn't use. To actually see one of these on the prediction widget, add its flag to that ALLOW-list, or open the base index.html. The cards below describe what each computes when enabled.

Modify cookbook

The common shapes of change, and where each lives:

Change what a plot shows (metric / axis)

Find the section's compute function (the naming map's last column). Edit the math there, adjust the payload key, then update the matching pushPoint render line and the plot's axis title. If the section is a parity section (§13, §14, §19, §20, §6), make the identical change in the browser's runLocal mirror too, or captures and live runs will disagree.

Add a whole new panel

# server.py, inside run_stream's per-step block:
g_mine = None
if mineflag and <gate>:
    g_mine = {"y": float(my_metric)}          # build the payload
# ...then add "g_mine": g_mine to the record dict (~line 5311+)
# parse the flag in _parse_params (~5950+): "mineflag": g("mineflag","0")=="1"
// widget: add the DOM (a <div id="p_mine" class="plot">), build it in initLivePlots,
// and render it in pushPoint:
if(D.g_mine){ extP('p_mine', {x:[[t]], y:[[D.g_mine.y]]}, [0]); }

Tune the Q-eigenspectrum

Raise/lower the full-spectrum size limit at QSPEC_FULL_CAP (server.py ~1928) — above it, non-MLP and huge-p nets fall back to a top⊕bottom-qspeck sample. Snapshot density is qspecevery (0 ⇒ auto ≈60/run). For very large p the eig runs in fp32 (fast on GPU) above the p>6000 threshold.

Change a section toggle's behavior

Remember the naming map: the checkbox enX and server flag sK rarely share a number. Edit the browser serialization (o['sK']=chk('enX')), the server parse, and the run_stream gate. Several predictions force their flag to '1' so they always compute — the checkbox only hides the panel.

The runnable companion: reference_predictions.py

reference_predictions.py re-implements this math in plain autograd on a tiny MLP — no SSE, no Lanczos, no widget plumbing — so you can read each formula as one obvious block and experiment directly.

# train a tiny net and watch sharpness cross the EoS line:
python reference_predictions.py --steps 60 --width 24 --lr 0.05
python reference_predictions.py --loss ce            # multiclass variant

Its layout mirrors this guide: Part 1 is the model / data / losses; Part 2 is the core objects (jacobian, residual, ntk, M_r, loss_hessian, sharpness, precond_half); Part 3 is one function per section (named in each card's reference.py row); Part 4 is a demo loop. Start at weighted_fn_hessian — it's the identity from §0 and nearly everything spectral is built on it.

Caveats. This guide is a map, not the territory: line numbers drift, so anchor on the named functions and DOM ids. The two widgets share one server.py; almost every MSE-vs-multiclass difference is a CE Fisher / natural-gradient switch keyed on loss.name=="ce", or the residual definition r = onehot − softmax(f). When you change a parity section, change both the Python and the JS mirror.

Found something off, or want a section expanded? That's the point of this file — mark it up and send it back.
